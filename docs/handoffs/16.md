§3 段 C 实证立项
§3.1 主门 [3] connect_done 实证(关键新发现)
段 C 首次实证:_connect 不是慢,是内部有 30s timeout 在等 account cache 注册。
异常原文:
RuntimeError("Account BINANCE-SPOT-master not registered in cache after 30.0s timeout")
任务状态:
done=True, cancelled=False, exception=RuntimeError(...)
时间线:
01:56:12  start exec_client + connect()
01:56:12  WARN: BinanceSpotInstrumentProvider: Not requesting trade fees for TESTNET
            ↑ load_all=True 配置生效的证据
01:56:43  ERROR: _connect: Account ... not registered in cache after 30.0s timeout
            ↑ 触发 30s 后,精确对应内部 timeout
01:57:12  WARN: No active subscription to unsubscribe from
            ↑ stop 触发(60s IDLE 结束)
机制定性:

这是 _connect 内部行为,与 IDLE_SECONDS 长度无关
段 A(5s)没看到是因为 timeout 还没触发,_connect 仍 running 时就被 stop cancel
段 B(30s)没看到是因为 NT logging 未初始化,ERROR 被静默吞噬(component.pyx L1437 早退逻辑)
段 C 看到是因为脚本调了 init_logging(level_stdout=LogLevel.WARNING),WARNING/ERROR 两级输出

§3.2 F2 假设证伪 + 真元凶定位
F2 假设(15.md §4):BinanceSpotInstrumentProvider: No loading configured WARN 是 _connect 卡顿元凶,加 load_all=True 后 _connect 应能 done=True。
实测证伪:

load_all=True 配置生效(WARN 变化已证)
但 _connect 仍在 30s 时抛 RuntimeError
真元凶 = account cache 注册路径未走通

矛盾点与推断:

spy 截到了 1 条 AccountState via Portfolio.update_account(说明 HTTP account state query 成功了,account 数据回包到达)
但 cache 没注册到 → _connect 的 30s 等待超时
推断(未实证):NT 内部本应有 ExecutionEngine 或 Portfolio 组件 register Portfolio.update_account endpoint,接收 AccountState 并写入 cache;裸 stubs 环境下无此组件;且段 B/C 的 spy 把 endpoint 抢注了,导致即使 NT 后续想 register 也会 KeyError(我们先到先得)
这条推断的实证需 P2 对照实验(关掉 spy 看 _connect 是否能 done),P2 已被排除(对齐"不陷调参循环"纪律)

§3.3 NT logging 价值兑现(通用纪律提升)
段 C 看到的 ERROR: _connect: Account ... not registered in cache after 30.0s timeout,段 B 当时被静默吞噬。差异原因:段 C 脚本调了 init_logging(level_stdout=LogLevel.WARNING, colors=False),段 B 也调了——但段 B 的 ERROR 在段 B 跑的时候没出现(因为段 B 的 IDLE 30s 没到 _connect 内部 timeout 触发点)。
通用纪律提升:所有 NT 相关脚本默认开 init_logging()。这条本来在段 B 是单独脚本的事,现在上升为通用规则。
