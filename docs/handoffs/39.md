## 4. 核心成果 — loop 崩终结（重大复盘）

### 4.1 根因：三轮全打错靶

v1（路径 A）/ v2（路径 B）/ F1 instrument provider 注入三轮调试，均集中在"注入没进 RiskEngine Cache"方向。
真正根因在别处：

> **on_done 闭包裸 loop.stop()** — `cli.py` 的 `on_done` 内通过 `asyncio.get_running_loop().stop()` 强停 NT kernel.loop，在 `node.run()`（即 `run_async()`）半途截断，导致：
> - `Event loop stopped before Future completed`
> - 8 个 engine task 留悬（`Task was destroyed but it is pending!`）
> - RuntimeError 上浮

这条 loop.stop() 是 PHASE-3 / STOP-B 阶段遗留的粗暴停机模式，在 b3b-live 里不适用（NT live node 有自己的 kernel 生命周期管理）。

### 4.2 修复（F5）

- **cli.py on_done**：去掉 `with contextlib.suppress(RuntimeError): asyncio.get_running_loop().stop()`，去掉 `import asyncio` / `import contextlib`。
- **OneShotStrategy**：`on_order_accepted` / `on_order_rejected` 改走 `self.shutdown_system(reason=...)`，让 NT kernel 自己 `stop_async()`，cancel 悬挂 task，干净退出。
- 效果：EXIT_CODE=0，全 engine STOPPED，无 RuntimeError，无悬挂 task。

### 4.3 F3 裁定：注入仍必需

HERMES_SKIP_INJECT=1 绕过注入路径 → DENIED：`Instrument ETHUSDT.BINANCE not found`。
根因：NT BinanceSpotInstrumentProvider.load() 走自己的 internal cache，不写入 RiskEngine 读的 kernel.cache；ExecClientConfig 的 `instrument_provider` 只决定 ExecClient 侧加载，不保证 cache 可见。
结论：`node.kernel.cache.add_instrument()` 是唯一可靠路径，注入块保留，HERMES_SKIP_INJECT 作诊断开关留存。
