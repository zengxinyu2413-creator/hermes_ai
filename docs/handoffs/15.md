§3 段 B 实证立项
§3.1 主判据 spy_ok 实证

spy_records = [("Portfolio.update_account", "AccountState")] —— 1 条
机制链证:msgbus.register(endpoint, handler) 抢注 → exec_client _send_account_state → msgbus.send(endpoint="Portfolio.update_account", msg=AccountState) → spy 截获
时序:_connect 起步后某时间点(< 30s)发生,具体早晚未细测

§3.2 endpoint 拓扑实证(零发单场景)

Portfolio.update_account —— 会到达(实证):_connect 内 HTTP account state query 触发,无需 WS 活着
ExecEngine.process —— 不会到达(实证为空,符合预期):需 order 活动,零发单场景下永远空
其他 endpoint(ExecEngine.reconcile_execution_* 系列、ExecEngine.reconcile_execution_mass_status)—— 段 B 场景未触发,留待 mass status / reconcile 场景验

§3.3 send vs publish 机制纠正
_send_* 方法全部走 msgbus.send(endpoint=...),不走 publish(topic=...)。源码位置:nautilus_trader/execution/client.pyx L907-L941。
原 14.md §4 的 subscribe("events.order*") 方案在机制上行不通(已纠正):那个 topic 是 ExecutionEngine 在 send 之后再 publish 出去的,裸测试无 ExecEngine,subscribe 永远捕不到。
保留这条警示后续接手者不要重蹈:在 NT 上做 exec_client 监听,优先用 msgbus.register(endpoint, handler) 抢注 endpoint,不是 subscribe(topic, handler)。
§3.4 NT logging 静默吞噬机制(单独强调)
未调 init_logging() 时所有 self._log.* 静默丢弃(component.pyx L1437 早退逻辑),grep stderr 不能作阴性证据。
段 A 不受牵连的实证:段 A 的零发单红线是靠静态 grep 脚本源码立住的(证据形态 a)—— 即段 A 脚本函数体里压根没有 submit_order/cancel_order/new_order/modify_order 调用,L6 仅 docstring 注释命中。这条静态保证与 NT logging 是否静默无关。
故:段 A 完全收口的状态不受这次发现牵连,无需回去补刀。后续接手者如怀疑段 A 红线松动,请回看本节,不要重启段 A 重新跑。
段 B 脚本已显式调 init_logging(level_stdout=LogLevel.WARNING, colors=False),确保 NT 内部 WARN/ERROR 可见(本次跑出的三条 WARN 即此机制产物)。
§3.5 teardown 跨场景成立
段 A teardown 模式(asyncio.wait(timeout=10) 确定性等待 + exec_client.stop())在段 B 场景(_connect 未 done)下仍能干净收口:lingering=0,is_running=False,POST-STOP WS snap 干净。
这是段 A 模式可复用性的一次实证 —— 段 C 起手脚本可继续照搬这一 teardown 块。

F1、F2 解决后大概率能进一步实证(_connect done=True 之后看 WS 主判据是否翻转)

L1 — base_url testnet 硬断言空挂(从段 A 沿袭)

段 A 和段 B 都构造 http_client 做 assert "testnet.binance.vision" in http_client.base_url,但 factory.create(...) 没传 http_client
实际决定 exec_client 用什么 base_url 的是 factory 内部走的逻辑,与外挂的 http_client 无关
当前在 BinanceEnvironment.TESTNET 配置下默认路径走对,但不是断言保证,是"配置 + 默认路径凑巧"
改法已知:factory.create 后从 exec_client 反读实际 base_url 再断言

L2 — factory.create 异常处理粒度(段 B)

段 B 只接 except KeyError,非 KeyError 异常会穿出 main 外层 try、不进 finally
实际后果:exec_client 未构造 → 没东西需 stop → 报告缺 verdict 段
当前可接受,后续清理时可扩到 except Exception,在分支里区分 KeyError 与其他
