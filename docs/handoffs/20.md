## §7 本会话事故 / 教训记录

### §7.1 E0 侦察漏了第三个 filter(PERCENT_PRICE_BY_SIDE)

E0 只查了 LOT_SIZE / MIN_NOTIONAL / tick,没查 PERCENT_PRICE_BY_SIDE。E1-wet 第一跑就撞上。**教训**:Binance filter 不止精度三件套,报价偏离规则(PERCENT_PRICE_BY_SIDE)也是硬拒单项;"为了不成交把价压到极低"会触发它。下次侦察下单 filter 要查全 exchangeInfo 的 filters 数组,不只精度。

### §7.2 但 dry→wet 分阶段的价值得到验证

先 dry 验证构造链(strategy_id 绑定),再 wet 真下单。dry 排除了"陌生订单路径"风险,wet 才暴露真实 filter 问题。**如果直接 wet,strategy_id 和 filter 两个问题会纠缠在一起难定位**。分阶段是对的。

### §7.3 主理人差点跳核审闸口(及时拦住)

E1-wet 脚本 Claude Code 写完后,主理人直接发了 `run it`,跳过了"贴报告 + Claude 核审"。Claude 拦下,坚持先核审(py_compile + 真调用位置 + filter 真取值 + teardown 没改坏)再跑。**教训**:wet 阶段(真下单)的核审闸口最不能省,越接近真实动作越要守 §1.5。
