## 4. 核心成果

### 4.1 ③ LC-RISK-4 — 截断 race 修复（resolved）

根因（字面）：`FileStateStore.save()` 旧码 `open("w")` 在拿 flock **之前**就把文件截到 0（advisory flock 挡不住 open 的截断），并发 `load()` 即便持 LOCK_EX、正在 read，文件也会被掏空 → `json.loads("")` 崩。锁保护了 write 却没保护 truncate，破坏性操作落在锁外。

修法（B 路线 / 单写假设）：`save()` 改原子写 = 同目录 tempfile → `flush` → `os.fsync` → `os.replace`（POSIX/Windows 原子 rename）；`load()` 去 flock，直接 `read_text`。reader 永远读到一份完整的旧或新文件，截断态彻底消失。fcntl 全删 → LC-RISK-2（多进程 flock 串行）由原子性取代（单 TradingNode 的单 RiskGuard = 单写；并发 writer = last-write-wins，不丢损坏只是后写胜）。接口签名（load/save）不变 → guard.py 零改 → ce9 零触碰。

### 4.2 ② LC-XPLAT-1 — risk_state 解 / seen_store 据暂缓

- `risk_state_store.py`：随 4.1 去 fcntl → 本文件 LC-XPLAT-1 **resolved**。
- `seen_store.py`：**按设计暂缓，非遗漏**。理由：它是 append-only（`open("a")` 追加一行）+ 显式多进程串行设计（LC-EXEC-5，concurrent 测试断言「两进程并发不丢条目」），与 risk_state 的覆写 / 单写语义不同 → atomic-replace 不适用、单写假设不成立。当前 POSIX-only 在 Linux 部署工作正常，无 bug / 资金 / 正确性风险。仅当 Windows 成为真实目标时再动，走 Q（去 fcntl 靠 O_APPEND 小写原子性 + 重写 2 条 lock-leak 测试）或 P（跨平台锁 helper）。
- 注：两文件「LC-XPLAT-1」状态不同是**有意决策**（risk_state 真解、seen_store 据保 POSIX-only），非待修矛盾。本条即此决策的持久记录（取代 CC 私有 memory 中的临时记录）。
