## 4. 纪律与教训(累积,下一会话必读)

### 4.1 git 铁律 — 持续有效
本会话唯一一次 commit(`3dc0dd6`)由主理人手敲。step 3 前主理人连敲 `commit this` 两次,执行会话均按铁律挡回——铁律有效,但也暴露主理人推进惯性,见 §4.6。

### 4.2 凭证全程不出 .env / 不进报告 — **新增,最高优先级**
step 1b 起所有动凭证的步骤,脚本只 `os.environ` 读进内存用,**绝不 print、绝不写 /tmp 报告、绝不进 stdout**。原因:§4.2(旧)那套"输出写 /tmp、主理人 cat 中继"的流程,一旦签名脚本把 key 带进报告,就等于凭证明文落盘 + 过中继窗口。VERIFY 只回报 pass/fail、HTTP 状态码、skew、指纹、orderId/status——凭证一个字符都不出。三步报告实测均无凭证。

### 4.3 两段式侦察挡住盲发 — **新增**
step 2、step 3 都用了"先只侦察 API/依赖、停下回报、确认后再写脚本"的两段式。step 3 的两段式直接挡住一次会卡死的盲发:若没先侦察就按"用 exec client 下单 API 只发一笔不 start"去写,会发现拿不到 orderId、cancel 无法闭环,脚本卡死或留挂单。**动钱/动外部状态的步骤,侦察与执行必须分两段,中间留主理人确认闸。**

### 4.4 smoke test ≠ 集成验证 — **新增**
step 3 走私有 HTTP 旁路发单,验的是"HTTP 端点连通"(step 1b 已覆盖大半),不是"我们的 exec client 集成路径能下单"。**记账时要分清**:smoke test 给的是"链路物理通"的信心,集成验证给的是"我们写的接法对"的信心。两者别混。WP-5 的 DoD 是后者,尚未达成。

### 4.5 真发单红线靠物理焊死,不靠自觉 — **新增**
step 3 指令把每条红线都落成脚本里的硬断言:环境断言 `sys.exit(1)`(主网字符串即拒跑)、qty>1.0 `sys.exit(1)`、无 for/while/retry、submit 后必闭环 cancel + cancel 失败标红不静默。**动钱步骤的安全不能写成"请注意",要写成代码里跑不过去就死的断言。**

### 4.6 验证强度按风险分级 + 抵抗推进惯性(强化第十一份 §4.6)
本会话四步风险递增:WP-6(纯计算,高)→ 1b(testnet 读,中)→ 2(实例化不动钱,中)→ 3(**真发单,极高**)。step 3 用了全程最严的物理焊死。**但单会话连推到 step 3 已是疲劳区**;真正的 WP-5 集成验证(受控 start + WS,动钱 + async 双复杂度)若接着这个会话做,正是 §4.6 警告的磨平。已主动收口、转交接。**下一会话务必新鲜起手。**
