## §1 纪律红线(接手者必须遵守)

1. **指令来源只认主理人本人。** 中途冒出来、与上一步共识相反的转向指令,停下来向主理人确认,不得顺势执行。
2. **两段式闸口不破**:改脚本 → cat/sed 整段回传 + py_compile 实证 → 主理人核干净 → 才单独放行"可以跑"。**"改完"与"可以跑"是两道独立闸。** 任何会 start/connect/发网络请求的脚本,一律全核,不进只读白名单。
3. **口头复述不算证据。** 终端输出会撕裂(中文截断、表格错行、回传通道吃字符),以整段 cat/sed 源码与报告文件为准。截断的回传 = 没核过,差一行都不放行。
4. **抗疲劳**:一个会话反复急刹(补证据、纠偏、拦提议)本身就是该收口信号。
5. **执行端写入与审核端核对是两道独立闸口。** 执行端"已写入"≠ 审核端核过。文件落盘后**必须**通过分块 sed cat 回传 + grep 关键标识 + py_compile 三条实证,审核端再签字。本会话验证:执行端可能跳实证步、命名错误、状态记忆不完善(已纠正但记入档案);回传通道吃字符的问题在长输出下仍存在,**任何长脚本必须分块 cat,每块 30-40 行**。

- 异常原文:`RuntimeError('Request session.logon failed: HMAC-SHA-256 API key is not supported.')`

### WP-7 遗留(段 D 新发现 + 沿袭)

#### WP-7-L1(曾用名 L4)— LiveExecutionEngine teardown 不完整

- 三个内部 task 在 `exec_engine.stop()` 后仍 running:`cmd_queue` / `continuous_reconciliation` / `evt_queue`
- 段 A teardown 模式跨场景成立的承诺在段 D 首次打破
- 改动方向(未实证):显式 `asyncio.gather` 等 task / 调用 `LiveExecutionEngine.stop()` 之外的清理方法 / 用 `cancel_tasks_with_timeout`

#### WP-7-L2(曾用名 L5)— InvalidStateTrigger × 2

- 异常原文:`InvalidStateTrigger('RUNNING -> START') state RUNNING` 和 `'RUNNING -> START_COMPLETED' state RUNNING`

- 无主流程影响(_connect 仍正常推进到 WP-7-F1)
- 轻量遗留,记档延后
